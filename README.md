# PayRelay

C로 만든 **PG(전자결제대행) 승인 중계 서버**입니다. 가맹점 단말이 보낸 고정길이 전문을 받아 검증하고, VAN(카드사 중계망)에 상호 TLS로 중계하고, 결과를 MySQL에 기록합니다. 응답이 늦으면 망취소를 보내고, 하루 거래는 VAN 정산 파일과 대사합니다. 공격 트래픽은 게이트웨이가 직접 판단해서 리눅스 커널(nftables) 단계에서 차단합니다.

> **처음 써 보시나요?** [테스트 가이드](docs/TEST_GUIDE.md)를 따라 하면 설치부터 결제·취소·망취소·공격 차단·정산 대사까지 화면을 보며 직접 확인할 수 있습니다.

```
 가맹점 POS ──TCP 전문──►┌──────────── pg-gateway (C, Linux) ─────────────┐──mTLS 전문──► VAN 시뮬레이터 (C)
  (테스트 단말,          │ reactor: epoll 1스레드                          │                 │ 원장, 정산 파일
   공격자 컨테이너)      │   연결 한도 · 슬로로리스 · 프레임 검증          │                 ▼
       ▲                 │      │ 작업 큐           ▲ eventfd              │           VAN_YYYYMMDD.txt
       │                 │      ▼                   │                      │                 │
       │   nftables ◄────│ guard: 위반 집계 → 차단  워커 풀 (기본 32)      │                 │
       │   (커널 차단)   │                  MAC · 속도 제한 · 멱등성      │                 │
       │                 │                  승인 · 취소 · 망취소          │                 │
       │                 └──────────────── │ prepared statement ──────────┘                 │
       │                                   ▼                                                │
       │                              MySQL 8.4  ◄── 읽기 전용 ── 관리 콘솔 (Node.js) ◄─────┘
       └────────────────────────────── 내부 제어 포트 (통계 · 차단 해제) ──┘   대시보드 · 대사 · 테스트 단말
```

## 구성

| 구성 요소 | 언어 | 하는 일 |
|---|---|---|
| `src/gateway` | C11, Linux | epoll 기반 TCP 서버, 워커 스레드 풀, MySQL C API, OpenSSL mTLS, nftables 연동, 내부 제어 포트 |
| `src/common` | C11 | 전문 코덱(고정길이·MAC), 카드번호 검증·마스킹·토큰, 토큰 버킷, TLS 입출력 |
| `src/vansim` | C11 | VAN/카드사 시뮬레이터: mTLS 서버, 승인·취소·망취소, 원장, 일별 정산 파일 |
| `db/schema.sql` | MySQL 8.4 | 거래 상태 머신, 멱등성 키, 이력·보안 이벤트, 정산 뷰, 최소 권한 계정 |
| `admin` | Node.js 20, JavaScript | 관리 콘솔: 대시보드, 거래 조회, 보안 이벤트·차단 해제, 정산 대사, 테스트 단말, 공격 시뮬레이션 |
| `tools` | Python 3 | 독립 구현한 전문 코덱, E2E·부하 테스트, 공격 시뮬레이터 |

## 설계에서 신경 쓴 부분

### 1. 전문 (`src/common/telegram.c`)

```
LEN(4) | HEADER(48) | BODY(종류별 고정 길이) | MAC(32)
HEADER = 전문종별(4) 버전(2) 가맹점ID(10) 단말ID(8) 거래일련번호(6) 거래일시(14) 응답코드(4)
MAC    = HMAC-SHA256(가맹점 키, HEADER‖BODY)의 앞 16바이트를 대문자 16진수로
```

- 0200/0210 승인, 0400/0410 취소, 0420/0430 망취소, 0800/0810 망관리를 지원합니다. 문자는 왼쪽 정렬 후 공백, 숫자는 오른쪽 정렬 후 0으로 채웁니다.
- LEN은 512바이트를 넘을 수 없고, 필드마다 허용 문자가 정해져 있습니다. 숫자 칸에 문자가 있거나 주문번호에 따옴표가 있으면 DB까지 가기 전에 거부합니다.
- MAC은 `CRYPTO_memcmp`로 비교합니다. 앞에서부터 틀린 곳을 찾으면 바로 멈추는 비교는 응답 시간 차이로 정보가 새기 때문입니다.
- 같은 형식을 **C, Python, JavaScript로 각각 따로 구현**했습니다. 테스트는 Python으로 만든 전문을 C 게이트웨이에 보내고, JS 테스트는 그때 실제로 오간 전문을 그대로 재현하는지 확인합니다. 한쪽 구현의 실수가 다른 쪽 테스트에서 드러나게 하려는 구조입니다.

### 2. 연결 처리: epoll 리액터 + 워커 풀 (`conn.c`, `worker.c`)

- 소켓은 **epoll 스레드 하나만** 만집니다. 이 스레드는 막히는(blocking) 일을 하지 않고, 바이트를 모아 완성된 전문만 잘라 작업 큐에 넣습니다.
- DB 조회와 VAN 왕복처럼 기다려야 하는 일은 워커 스레드가 처리합니다. 응답은 큐에 넣고 `eventfd`로 리액터를 깨워 보냅니다.
- 연결은 `(세대 번호 << 32) | 슬롯 번호`로 구분합니다. 워커가 응답하기 전에 끊긴 연결이 같은 슬롯에 새로 들어와도, 옛 응답이 엉뚱한 단말로 가지 않습니다.
- 작업 큐가 가득 차면 요청을 쌓아 두지 않고 연결을 끊습니다(백프레셔).

### 3. 결제 처리 (`worker.c`)

| 상황 | 처리 |
|---|---|
| 같은 주문을 다시 보냄 (POS 재시도) | `UNIQUE(merchant_id, order_no)`. 결과가 있으면 **그 결과를 다시 돌려주고 VAN에는 보내지 않음**. 금액이나 카드가 다르면 거부 |
| 10개 단말이 같은 주문을 동시에 보냄 | INSERT가 한 건만 성공. 나머지는 1004(처리 중) 또는 같은 결과 |
| VAN이 3초 안에 답하지 않음 | 가맹점에는 바로 9001로 응답(기다리게 두지 않음). 이어서 **망취소(0420)** 를 새 연결로 최대 3번 보냄. 확인되면 `NET_CANCELED`, 안 되면 `REVERSAL_FAILED` |
| 망취소가 늦은 원거래보다 먼저 VAN에 도착 | VAN 시뮬레이터가 망취소를 기록해 두고, 뒤늦게 온 원거래는 장부에 올리지 않음 |
| 같은 거래를 동시에 취소 | `SELECT ... FOR UPDATE`로 행을 잠그고 VAN 왕복 후 커밋. 한 번만 성공 |
| 상태 변경 | `UPDATE ... WHERE status = 'PENDING'` 같은 조건부 갱신(compare-and-set). 두 스레드가 같은 거래를 동시에 끝낼 수 없음 |
| 카드번호 | DB에 **저장하지 않음**. BIN 6자리, 끝 4자리, 별도 키로 만든 HMAC 토큰만 저장. 로그와 응답에도 마스킹된 값만 남김 |

### 4. 트래픽·패킷 제어 (`guard.c`, `conn.c`)

| 공격 | 대응 |
|---|---|
| 전문이 아닌 바이트 (HTTP, TLS, SQL 문자열 등) | 길이 필드 검증 실패 → 연결 종료, 위반 1회 |
| MAC 위조 | 1001 응답 후 연결 종료, 위반 1회 |
| Slowloris (전문을 시작만 하고 끝내지 않음) | 프레임이 5초 안에 완성되지 않으면 종료, 위반 1회 |
| 연결 폭주 | IP당 동시 연결 50개 초과분 거부, 위반 1회 |
| 요청 폭주 (정상 가맹점) | 가맹점별 토큰 버킷(초당 N건), 초과분은 9003. 정상 가맹점이 차단되지 않도록 **위반으로 세지 않음** |
| 위반이 1분 안에 5회 | **10분 차단**: 프로세스 내부 차단 목록 + `nftables` set에 만료 시간과 함께 등록. 이후 그 IP의 패킷은 커널이 버리므로 TCP 연결조차 맺어지지 않음 |

`nft`는 셸을 거치지 않고 `posix_spawnp`와 고정된 인자 배열로 실행합니다. 넘기는 IP도 `inet_pton`으로 검증한 값만 씁니다. nftables를 쓸 수 없는 환경(권한 없음)에서는 프로세스 내부 차단만으로 계속 동작하고, 로그에 그 사실을 남깁니다.

### 5. VAN 연동과 정산 대사

- 게이트웨이와 VAN은 **상호 TLS(mTLS)** 로 연결합니다. 둘 다 같은 사설 CA가 서명한 인증서를 제시해야 하고, 게이트웨이는 VAN의 호스트 이름까지 확인합니다. 다른 CA 인증서나 인증서 없는 접속은 TLS 단계에서 거부됩니다.
- VAN 시뮬레이터는 승인(A)·취소(C)·망취소(R)를 일별 정산 파일에 남깁니다. 관리 콘솔은 이 파일과 PG 기록을 **거래 단위로 대사**해 불일치와 필요한 조치를 보여줍니다. 망취소 응답까지 유실된 거래(VAN은 승인, PG는 미확정)가 여기서 잡힙니다.

### 6. 데이터베이스 (`db/schema.sql`)

- 거래 상태 머신: `PENDING → APPROVED → CANCELED`, `PENDING → DECLINED`, `PENDING → TIMEOUT → NET_CANCELED / REVERSAL_FAILED`
- `tx_events`에 모든 상태 변화, `security_events`에 위반·차단·해제를 남깁니다. 보안 이벤트는 별도 스레드가 기록하므로 공격이 몰려도 리액터가 DB를 기다리지 않습니다. 대기열은 1만 건으로 제한해 로그로 메모리가 고갈되지 않게 했습니다.
- 계정을 나눴습니다. 게이트웨이는 가맹점 조회와 거래 쓰기만, 관리 콘솔은 읽기만 할 수 있습니다.
- 모든 쿼리는 prepared statement로 실행합니다.

### 7. 관리 콘솔 (`admin`)

- Node.js 표준 라이브러리와 `mysql2`만 사용합니다. 세션 쿠키는 HttpOnly, SameSite=Strict이고, POST 요청에는 CSRF 토큰을 요구합니다. 로그인은 5회 실패하면 1분간 잠기고, CSP와 `X-Frame-Options`를 설정했습니다.
- 화면에는 서버에서 받은 값을 `textContent`로만 넣습니다. 가맹점이 보낸 주문번호 같은 값이 HTML로 해석되지 않게 하기 위해서입니다.
- 게이트웨이의 내부 제어 포트(토큰 인증, 줄 단위 JSON)로 통계를 조회하고 차단을 해제합니다.

## 실행

Docker Desktop만 있으면 됩니다.

```bash
docker compose up -d --build
```

- 관리 콘솔: http://localhost:8090 (데모 비밀번호 `admin1234!`)
- 게이트웨이 전문 포트: `localhost:9100`

모든 포트는 이 PC(127.0.0.1)에서만 열립니다. compose에 적힌 키와 비밀번호는 데모용 기본값입니다.

## 테스트 중 발견한 문제와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| 게이트웨이를 재시작한 직후 첫 요청에만 응답이 오지 않음 | 첫 연결(슬롯 0, 세대 0)의 ID가 0인데, 응답 큐가 ID 0을 "이 IP의 연결을 모두 끊기" 신호로 쓰고 있었음 | 신호를 별도 필드로 분리. 테스트 스크립트가 매번 게이트웨이를 재시작한 직후 E2E를 시작해 같은 문제를 다시 확인함 |
| 데모 가맹점 키가 로드되지 않을 뻔함 | 손으로 쓴 16진수 키가 64자가 아니라 62자였음. 게이트웨이는 16바이트보다 짧거나 깨진 키를 거부하도록 되어 있음 | 키를 스크립트로 생성해 길이를 검증한 값으로 교체 |
| 가맹점 이름 한글이 관리 콘솔에서 깨짐 | MySQL 초기화 스크립트를 latin1 클라이언트 문자셋으로 읽음 | 스키마 맨 위에 `SET NAMES utf8mb4` 추가 |
| 망취소가 늦은 원거래보다 VAN에 먼저 도착할 수 있음 (설계 중 발견) | 게이트웨이는 3초에 망취소를 보내는데 원거래는 5초에 처리됨 | VAN이 "원거래 없는 망취소"를 기록해 두고 뒤늦은 원거래를 장부에 올리지 않게 함 |
| E2E에서 동시 취소 테스트가 9003으로 실패 | 속도 제한(초당 20건)이 정상적으로 작동한 것. 테스트가 같은 가맹점으로 너무 빨리 보냄 | 동시성 테스트는 부하 테스트용 가맹점으로 분리 |
| 테스트 가이드를 처음 쓰는 사람 입장에서 따라 하다가: 테스트 단말로 MAC 위조를 5번 보내자 정상 결제까지 "응답 없음"이 됨 | 게이트웨이가 관리 콘솔 컨테이너도 위조 전문을 보낸 IP로 보고 차단함(의도한 동작). 다만 화면에 이유가 나오지 않아 초보자는 고장으로 오해할 수 있음 | 응답이 없을 때 차단 가능성과 해제 방법을 화면에 안내하고, 차단 목록에서 관리 콘솔 IP에 "(이 관리 콘솔)" 표시 |
| 부하 테스트에서 2개 연결이 거부됨 | 테스트 러너 연결 + 부하 연결 50개가 IP당 한도(50)를 넘음. 역시 방어가 의도대로 동작한 것 | 부하 연결을 40개로 조정 |

## 이전 프로젝트와 이어지는 부분

| 이전 프로젝트에서 남은 것 | 이번에 한 것 |
|---|---|
| 문서 암호화 1차 설계(inotify + MySQL C API)에서 파일명을 쿼리 문자열에 이어 붙여 SQL 인젝션이 가능했고, 바이너리 키를 `strlen`으로 다뤄 잘림 | MySQL C API를 prepared statement와 바인딩으로만 사용, 키는 길이와 함께 다룸 |

| C++ 트래픽 감사 에이전트(netaudit)는 패킷을 **보고 기록**만 함 | 이번에는 트래픽을 **직접 판단해 제어**: 연결·프레임 단위 검증, 속도 제한, nftables 차단 |
| Rust NAC에서 nftables를 다뤘음 | 같은 개념을 C 서버에 붙여 애플리케이션 판단이 커널 차단으로 이어지게 함 |

## 한계와 다음 단계

- **가맹점 MAC 키가 DB에 평문(16진수)으로 있습니다.** 실제로는 KEK로 감싸 저장하거나 HSM에 두어야 합니다(TrustGate 프로젝트의 KEK/DEK 구조를 그대로 쓸 수 있음).
- **TIMEOUT 상태로 프로세스가 죽으면** 망취소가 다시 시도되지 않습니다. 시작할 때 `TIMEOUT` 건을 찾아 망취소를 재개하는 복구 루틴이 필요합니다.
- 대사에서 찾은 불일치는 화면에 보여주기만 합니다. 망취소 재시도·강제 취소 같은 조치를 콘솔에서 실행하는 기능은 없습니다.
- 부분 취소, 할부 수수료, 가맹점 정산(지급) 계산은 구현하지 않았습니다.
- 가맹점 구간은 평문 TCP + MAC입니다. 실제로는 전용선·VPN이나 TLS를 함께 씁니다.
- IPv4만 지원합니다. 게이트웨이는 한 대로 동작하며, 차단 목록과 속도 제한 상태를 여러 대가 공유하지 않습니다.
